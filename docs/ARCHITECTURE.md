# 架构说明

LoreDock 使用 React / TypeScript 实现知识工作区，FastAPI 负责模型接入、已同步资料的检索和版本校验。Electron 复用网页构建结果，提供 Windows 桌面运行环境。

## 存储边界

| 数据 | 当前存储 | 更新入口 |
| --- | --- | --- |
| 空间、编辑正文、草稿、会话、知识卡片、模型偏好 | 浏览器或 Electron 的 IndexedDB | `frontend/src/storage.ts` 专用事务 |
| 已同步的资料版本、分块、FTS5、持久删除标记 | `library.sqlite3` | `backend/library.py` |
| 服务名称、地址、模型和密钥密文 | `settings.sqlite3` | `backend/store.py`；Windows DPAPI |
| 各资料版本的不可变文本副本 | 数据目录下的 `uploads/` | 后端以内容哈希组织，检查路径边界 |
| 阅读卡片的未保存草稿与批次 | 本次应用进程内存 | `useCardWorkshop.ts` / `cardWorkshop.ts` |

网页开发模式的后端数据目录默认是项目 `data/`，可用 `LOREDOCK_DATA_DIR` 修改。桌面数据位于 `%APPDATA%\LoreDock`。这些数据都不进入源码仓库。

## 编辑与版本一致性

`DocumentReader` 使用 CodeMirror 编辑正文，`useDocumentDraft` 按文档 ID 管理缓冲区。输入后约 150 ms 暂存草稿，停顿约 1 秒提交正文；手动保存和离开页面会等待事务完成。

保存要求与当前已保存版本一致。保存 A 的过程中继续输入 B，A 的回执不能覆盖 B；真实外部版本冲突需要选择采用草稿或已保存版本。只有正文、资料身份、标题、文件名、类型与空间均一致时，才允许对齐不同的本机／后端版本号。

编辑保存首先写 IndexedDB。正文检索或明确开启资料参考时，`localIndex.ts` 再把已保存版本同步至后端。检索请求携带 `document_versions`，后端在同一读取事务中核对资料、空间和版本，避免查询到当前范围之外的残留副本。

## 三种问答上下文

| 模式 | 内容来源 | 用途 |
| --- | --- | --- |
| `none` | 问题和符合当前上下文范围的历史 | 默认普通问答；可独立附加阅读选文 |
| `snapshot` | 明确提交的当前文档或历史摘录 | 阅读器开启“参考本文” |
| `indexed` | 通过范围、版本白名单校验的 FTS5 结果 | 主问答开启“参考资料” |

当前 UI 显式使用 `answer_mode: assistant`，没有资料也可回答。后端保留旧客户端的严格资料模式作为兼容路径。

选文单独携带正文、章节、附近原文、文档版本与草稿／历史标记。普通选文最多 2000 字符，附近原文最多 5000 字符。用户点击发送才调用模型。

相关知识卡片由前端本地匹配，最多展示 4 个可点击入口。模型请求不附带这些卡片的标题、记法或正文；旧版卡片依据历史与新版上下文隔离。

## 请求与引用

每轮提交固定 `session_id`、`request_id`、模型、档位和范围快照。前端只有在标识匹配时才能把返回结果写入对应会话；切换空间不改变已发出请求的依据。

后端仅接受本轮上下文实际存在的来源 ID，并保留原版本摘录。有效引用 ID 只是可追溯性校验，不代表模型结论在语义上一定受到原文支持。

资料删除先持久记录删除意图并撤下索引，再通过前端专用事务移除条目；迟到同步不能复活同一 ID。历史文件尚未全部物理清理，退索引响应会明确标记 `purge_pending`。

## 卡片生成与修订

粘贴、阅读选文、整篇分批均调用专用卡片生成接口。长文章按章节及预算切分，批次拼接仍为完整原文；失败或停止保留已完成批次，重试由用户发起。

草稿使用稳定 ID。修订接口只允许修改已提供的目标，合并时保留来源；前端同时校验会话、请求与修订号。草稿需要用户勾选确认后才能通过 IndexedDB 批量事务写入正式卡片，保存不会再调用模型或自动建立索引。

## 桌面运行边界

Electron 使用固定来源 `loredock://app/`，通过主进程代理本机随机端口的 FastAPI 服务，并附加每次启动独立的访问令牌。渲染页面关闭 Node.js 集成，开启上下文隔离和沙箱。窗口退出时回收所管理的后端进程。

这套结构面向单用户本机使用。尚未实现公网账号授权、向量检索、完整跨设备恢复或多服务业务拆分。
